## タスク概要

Primary LLM → Fallback LLM → ルールベースV1 の3層フォールバック機構の実装。各層で失敗した場合に次の層へ自動的にフォールバックし、最終的にルールベースにより成功率100%を保証する。フォールバックチェーンの管理、各層の呼び出し、成功率の追跡を行う。

## 実装詳細

### 1. フォールバックチェーン管理 🔵

**信頼性**: 🔵 *SYSTEM_CORE.md §4.2, PIPELINE_FLOW.md §4.1 より*

3層フォールバックチェーンを管理するFallbackChainクラスを実装する。

- `FallbackChain` クラス: フォールバックチェーンのオーケストレーション
- `execute(request: AnalysisRequest): Promise<AnalysisResult>`: チェーンの実行
- 3層構成:
  - Layer 1（Primary LLM）: 複雑度に基づくモデル選択（Flash/Pro）によるGemini API分析
  - Layer 2（Fallback LLM）: Primary失敗時の代替モデル（Primary=Flash → Fallback=Pro、Primary=Pro → Fallback=Flash）
  - Layer 3（ルールベースV1）: 全LLM失敗時の最終フォールバック（常に関連結果を返す）
- フォールバック条件:
  - API呼び出しエラー（ネットワーク、タイムアウト）
  - レスポンスパース失敗
  - バリデーションエラー（必須フィールド欠落）
  - レートリミット（429）リトライ上限到達

**実装ファイル**: `src/analysis/fallback-chain.ts`

### 2. 各層の呼び出し 🔵

**信頼性**: 🔵 *SYSTEM_CORE.md §4.2, PIPELINE_FLOW.md §4.1 より*

各フォールバック層の呼び出しロジックを実装する。

- `executePrimary(request: AnalysisRequest): Promise<AnalysisResult>`: Layer 1の実行
- `executeFallback(request: AnalysisRequest): Promise<AnalysisResult>`: Layer 2の実行
- `executeRuleBased(request: AnalysisRequest): Promise<AnalysisResult>`: Layer 3の実行
- 各層の呼び出しフロー:
  - 現在の層を実行
  - 成功時: 結果を返す
  - 失敗時: エラーをログ記録し、次の層へフォールバック
  - Layer 3（ルールベース）は必ず成功を返す
- タイムアウト設定:
  - Layer 1: 30秒
  - Layer 2: 30秒
  - Layer 3: 即座（ローカル処理）

**実装ファイル**: `src/analysis/fallback-chain.ts`

### 3. 成功率追跡 🔵

**信頼性**: 🔵 *SYSTEM_CORE.md §4.2, PIPELINE_FLOW.md §4.1 より*

フォールバックチェーンの成功率を追跡・記録する。

- `FallbackStats` インターフェース: 統計情報
  - `totalRequests`: 総リクエスト数
  - `primarySuccess`: Layer 1 成功数
  - `fallbackSuccess`: Layer 2 成功数
  - `ruleBasedSuccess`: Layer 3 成功数
  - `successRate`: 成功率（%）
- `getStats(): FallbackStats`: 統計情報の取得
- `resetStats(): void`: 統計のリセット
- ログ記録:
  - フォールバック発生時: 警告ログ（どの層からどの層へ移行したか）
  - Layer 3 到達時: エラーログ（LLM全層失敗の通知）
  - 成功時: 情報ログ（使用層、レイテンシ）

**実装ファイル**: `src/analysis/fallback-chain.ts`

## 注意事項

- フォールバックチェーンは同期的に実行し、並列呼び出しは行わないこと（API呼び出しの重複を避けるため）
- Layer 3（ルールベースV1）はいかなる状況でも必ず結果を返すことを保証すること（100%成功率）
- フォールバック発生時は必ずログを記録し、後から分析可能にすること
- 統計情報はメモリ上に保持し、プロセス再起動でリセットされる設計でよい
- タイムアウトは各層ごとに独立して設定し、累積タイムアウトにならないようにすること
