## タスク概要

`TranscriptionPipeline`（src/transcription/transcriber.ts）の ASR フォールバック順序が現行 `runWhisperTranscription()` 内の inline if/else（Priority 1〜3・transcriber.ts:123-168）に埋め込まれているのを、per-instance の `RecoveryStrategyChain` step 列（`whisper-inference` → `web-speech-file`（browser 環境のみ登録）→ `disclosed-placeholder`）に置換する。外部契約（`transcribe()` signature・`TranscriptionResult` 型・既存 4 leg priority test の挙動）は一切変えずに、error-recovery 基盤への接続（trace・stats・`errorRecoveryEventBus` event）と、既存 test が持たないギャップ分（throw 注入・budget 枯渇時の開示最終保証）の検証を新規 test file で成立させる。src 変更は transcriber.ts 1 file のみ（見立て +70 行）・新規依存ゼロ。

## 実装詳細

### 1. transcriber.ts — chain 構築と置換 🔵

**信頼性**: 🔵 *architecture.md「コンポーネント構成」・recovery-strategy-chain.ts public API（register :195・execute :222・ChainBuilder :130-159）より*

**実装ファイル**: `src/transcription/transcriber.ts`

- import 追加: `RecoveryStrategyChain` / `ChainBuilder` / `type ChainOutcome`（`'../quality/recovery-strategy-chain'`）・`meanSegmentConfidence`（`'../pipeline/quality-estimators'`）。`globalRecoveryChain` singleton は使わない（test 間 stats 汚染回避 — per-instance でも event は singleton bus へ流れる）
- module 定数 `TRANSCRIPTION_RECOVERY_TIME_BUDGET_MS = 120_000`（設定不可・A4: whisper.cpp CPU 推論は 30s default で切り捨て得る）
- constructor で `this.recoveryChain = new RecoveryStrategyChain()` + `register('transcription', this.buildRecoveryChain())`
- step 1 `whisper-inference`（`then`・必須）: `blob:` → `blobUrlToFile()` の File 化（現行 :128-133）を step 内で行い `whisperTranscriber.transcribe(audioInput)`。`isRealTranscriptionResult` を満たすとき `{ result: { segments }, fallbackUsed: false, confidence: meanSegmentConfidence(segments) }`、満たさないとき `undefined`。throw は chain が catch して failure step として trace する（recovery-strategy-chain.ts:336-352）— 現行の catch leg（transcriber.ts:164-167）は不要になる
- step 2 `web-speech-file`（`thenOptional`・browser 環境かつ `blob:`/`File` 入力のときのみ step 列に登録）: `browserTranscriber.transcribeAudioFile(File)`。成功（`success && segments.length > 0`）なら `{ result: { segments }, fallbackUsed: false, confidence: meanSegmentConfidence(segments) }`、それ以外 `undefined`
- step 3 `disclosed-placeholder`（`then`・必須）: engine を呼ばず `{ result: { segments: this.getFallbackSegments() }, fallbackUsed: true, confidence: 0 }` を常に返す（失敗しない）
- `runWhisperTranscription()` 本体: `chain.execute('transcription', { stage: 'transcription', timeBudgetMs: TRANSCRIPTION_RECOVERY_TIME_BUDGET_MS, minConfidence: 0 })`。`outcome.success === true` なら winning step の segments と `fallbackUsed`（`'disclosed-placeholder'` 勝利 ⟺ `isFallback: true`）を返す。`outcome.success === false`（budget 枯渇で mandatory step も skip・recovery-strategy-chain.ts:259-271）でも `getFallbackSegments()` と `isFallback: true` を返す（開示の最終保証 SD4）
- public getter `getRecoveryOutcome(): ChainOutcome | null`（直近 1 件のみ保持・accumulation しない — 累積は chain の `getStats()` が既に持つ）
- `transcribe()` / `updateConfig()` / `getFallbackSegments()` / `validateAudioFile()` は不変

**実装ファイル**: `tests/transcription/transcriber-recovery-chain.test.ts`（新規・~90 行）

## 単体テスト要件

### テストケース1: trace 順序の機械検証（AC-D5-1）🔵

**信頼性**: 🔵 *AC-D5-1「trace の attempted step id 列を環境別に pin する test」より*

**Given**: engine mock で whisper が placeholder 結果を返す状態（Node 環境 / browser 環境の両方）
**When**: `transcribe()` を実行し `getRecoveryOutcome().trace` の attempted step id 列を取得
**Then**: Node 環境で `['whisper-inference', 'disclosed-placeholder']`（web-speech step は未登録）、browser 環境（`blob:` 入力）で `['whisper-inference', 'web-speech-file', 'disclosed-placeholder']` であること

### テストケース2: throw 注入 → 次 engine 移行（AC-D5-2・ギャップ分）🔵

**信頼性**: 🔵 *AC-D5-2「throw 注入 leg（既存 4 leg に存在しないギャップ分）」・design-interview A2 より*

**Given**: browser 環境・whisper mock が `transcribe()` で **throw** する状態
**When**: `transcribe()` を実行
**Then**: browser engine が呼ばれその real 結果で成功すること（`success: true`・`fallback` なし）・trace に `whisper-inference` の attempted/failure 記録が残ること。既存 4 leg（placeholder 結果注入 3 leg + Node 非 construct 1 leg）は無修正 green

### テストケース3: 全滅 → 開示 placeholder（AC-D5-3）🔵

**信頼性**: 🔵 *AC-D5-3「全滅注入 leg」・dataflow.md 機能3 より*

**Given**: browser 環境・whisper mock が throw / placeholder・browser mock が `success: false`
**When**: `transcribe()` を実行
**Then**: `winningStepId === 'disclosed-placeholder'`・`fallbackUsed === true`・`confidence === 0`・結果が `fallback: true`・`success: false`・`segments[0].confidence === 0` で開示されること

### テストケース4: budget 枯渇 → pipeline 側開示の最終保証（AC-D5-3・SD4）🔵

**信頼性**: 🔵 *AC-D5-3「開示最終保証 leg」・recovery-strategy-chain.ts:259-271（budget 枯渇で mandatory step も skip → outcome.success=false）より（注入の具体機構のみ 🟡 実装時判断 → 実装で 🔵 化）*

**Given**: chain が budget 枯渇で `success: false` に終わる状態（例: `Date.now` を呼び出し毎に budget 超過分だけ進行させる spy で deadline を経過させる）
**When**: `transcribe()` を実行
**Then**: 開示 placeholder segments（confidence 0）が `fallback: true` で返ること — 開示が chain の健全性に命運しないこと

### テストケース5: minConfidence = 0 固定の順序権威（AC-D5-4）🔵

**信頼性**: 🔵 *AC-D5-4・design-interview A3（confidence 逆転 trap）より*

**Given**: whisper mock が real 結果（`placeholder` なし・segments の confidence は `undefined`）を返す状態
**When**: `transcribe()` を実行
**Then**: whisper step が勝つこと（`winningStepId === 'whisper-inference'`・`fallback` なし）— step confidence 0 の実推論結果が下位 engine に逆転されないこと

### テストケース6: event witness と getter（AC-D5-5）🔵

**信頼性**: 🔵 *AC-D5-5「event 順序 witness + getter pin」・recovery-strategy-chain.ts の event emit 実装より*

**Given**: `errorRecoveryEventBus` に listener を登録した状態で whisper が placeholder → browser が失敗
**When**: `transcribe()` を実行
**Then**: `stage: 'transcription'` の `recovery:attempt`（step ごと）→ 各 step の成否で `recovery:success` / `recovery:failure` が emit されること・`getRecoveryOutcome()` が直近 outcome（`winningStepId: 'disclosed-placeholder'`）を返すこと（2 回目の `transcribe()` で上書きされること）
