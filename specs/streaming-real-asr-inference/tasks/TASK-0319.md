## タスク概要

`StreamingTranscriber.transcribeStream`（streaming-transcriber.ts:147-254）のシミュレーション chunk loop（`createAudioChunks` + `processAudioChunk` + 10x realtime の `setTimeout` :224）を廃止し、環境判定による 3 分岐へ置き換える: (1) browser + Web Speech available → TASK-0318 の shared file engine 経由（final result ごとに実 `onSegment` / `onProgress`）(2) Node → `whisperTranscriber.transcribe` への丸ごと委譲（単発推論・完了時 1 回 emit）(3) いずれも不可 → `placeholder: true` 付き開示 placeholder。あわせて constructor（:111）と `validateStreamingSupport`（:625-）の bare `window` 参照を `typeof window !== 'undefined'` guard の内側へ置き、Node での構築を可能にする。

## 主要実装項目

### 1. 環境別 3 分岐への routing 書き換え 🔵

**信頼性**: 🔵 *architecture.md「routing 改修」節・dataflow.md「データフロー全体」（分岐条件が明記）より*

`transcribeStream` 冒頭で環境判定し、3 経路のいずれかで `TranscriptionResult` を組み立てる:

1. **browser + Web Speech available**（`typeof window !== 'undefined'` かつ recognition 構築成功）: `transcribeFileWithWebSpeech(audioFile, { onFinalSegment })` に委譲。final result ごとに `onSegment(segment)` + `onProgress`（実イベントのみ）を転送
2. **Node**（`typeof window === 'undefined'`）: `whisperTranscriber.transcribe(audioFile)`（singleton・whisper-transcriber.ts:704）へ丸ごと委譲。`placeholder !== true` なら segments をそのまま流用し完了時 `onProgress` 1 回。`placeholder: true` なら 3 へフォールスルー（whisper 側固定文を二重持ち込みしない）
3. **開示 placeholder**: 現行 `processAudioChunk` 相当の固定文生成（:441）を残置し、結果に `placeholder: true` を付与。`PLACEHOLDER_CHUNK_CONFIDENCE`（:25）と `detectTranscriptionLanguage` 委譲（:242）は維持

いずれの経路も `placeholder` flag を必ず設定（実経路 `false` / 開示 `true`）。`getAudioDuration` 失敗（分岐 3 の chunk 数算出のみで使用）は `placeholder: true` で返す（dataflow エラーフロー）。

**実装ファイル**: `src/transcription/streaming-transcriber.ts`

### 2. constructor / validateStreamingSupport の window guard 🔵

**信頼性**: 🔵 *streaming-transcriber.ts:111（`'webkitSpeechRecognition' in window` — Node で ReferenceError）と :625-（`validateStreamingSupport` の bare 参照）の実在より*

- constructor の recognition 構築（:111-116）を `typeof window !== 'undefined' && (...)` の内側へ
- `validateStreamingSupport` の `'webkitSpeechRecognition' in window` 等 3 参照を同 guard の内側へ（Node では各 `false` 扱いで recommendation を返す — throw しない）

## 基本的なテスト要件

### テストケース1: browser 分岐 — engine 委譲と実イベント進捗 🔵

**信頼性**: 🔵 *TC-408-01 (a)・dataflow.md 経路1 より*

**Given**: jsdom + Web Speech available な環境（SpeechRecognition mock が final result を 2 つ発行）
**When**: `transcribeStream(file, onProgress, onSegment)` を呼ぶ
**Then**: `onSegment` が final result ごとに 2 回・`onProgress` が実イベント単位で発火し、結果の `placeholder` が `false` であること

### テストケース2: Node 分岐 — whisper 委譲と単発 emit 🔵

**信頼性**: 🔵 *TC-408-01 (b)・SD2/SD3 より*

**Given**: Node 環境（`typeof window === 'undefined'）。`whisperTranscriber.transcribe` を mock（`placeholder: false` の実測相当結果を返す）
**When**: `transcribeStream(path)` を呼ぶ
**Then**: 委譲結果の segments がそのまま採用され、`onProgress` が完了時 1 回のみ emit されること（chunk 分割された合成進捗が出ないこと）

### テストケース3: gate 閉フォールスルーと開示 placeholder 🔵

**信頼性**: 🔵 *TC-408-01 (c)・TC-408-03 result flag・SD5 より*

**Given**: Node 環境で `whisperTranscriber.transcribe` が `placeholder: true`（gate 閉）を返す / または Web Speech 不可能な browser 環境
**When**: `transcribeStream` を呼ぶ
**Then**: 結果が `placeholder: true` を持つこと。固定文 segment が `PLACEHOLDER_CHUNK_CONFIDENCE` 付きで残ること

### テストケース4: Node 構築可能性 🔵

**信頼性**: 🔵 *SD6（bare `window` の ReferenceError）より*

**Given**: Node 環境
**When**: `new StreamingTranscriber({})` と `validateStreamingSupport()` を呼ぶ
**Then**: いずれも throw しないこと
