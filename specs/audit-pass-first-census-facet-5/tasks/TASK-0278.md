## 背景

make-run steering 直近の「audit-pass-first パターンを未着手の facet に適用」指摘の具体化。REQ-391〜394 の手動 audit が度々「`// Would be calculated from actual results`」「`// assumes`」「`// Simulated`」形の confession comment を**捏造の隠蔽**として発見してきた滴りに対し、stale-comment を class として pin する diagnostic 価値がある。既存観測で残件 0 件（after REQ-391〜394 撲滅同梱後）のため REQ-394 同型で **confirmed-zero 固定**（手動 audit で残件 0 を確認した上で新規 site を意識的分類する gate のみ ship・撲滅同梱なし）。

## 実装

1. **stale-comment-census guard 新設** — `tests/guards/stale-comment-census.test.ts`: REQ-396-001 の 4 軸（confession / disclosure / marker / self-claim）で 1 行 discovery。検出範囲は `//` 行 comment と `/* */` block comment 冒頭行のみ・`**` 開始 doc-comment は対象外（REQ-396-004）。ALLOWED（intentional design / defect-N refer / legal header）と ERADICATED（confession / disclosure / TODO marker / self-claim without follow-through）の 2 分類・reason 衛生 = REQ-391 ALLOWED 5 分類命名規約踏襲（REQ-396-002）
2. **walkProductionSurface 単一実装再利用** — REQ-302 で REQ-391 既存実装を `import` で再利用・新規 enumeration 追加禁止
3. **counter liveness** — REQ-394 規約準拠（quoted key・bare identifier key は計上・4-space 継続行・comment 行は非計上・不在 block は fail-loud）。複数軸同時 hit は最初の軸で 1 度のみ計上（REQ-396-005 AND 結合禁止）
4. **multiline discovery 上限の正直 doc 化** — header に「multiline confession は検出上限・block-comment 冒頭行のみ」を明記（REQ-203 踏襲）
5. **negative anchor backup regex** — REQ-204 で「deprecated」/「legacy」/「obsolete」/「won't fix」/「don't use this」/「outdated」/「no longer used」self-claim 検出の backup を 1 個以上同梱

8. **MW-060 mutation 検証（3 独立 RED 実測）** — (a) ALLOWED row を 1 件追加 without spec 編集 → **1 failed**（phrase mismatch）(b) requirements.md 数値のみ更新 without roster 変更 → **1 failed** (c) `census-pin:F5:` marker 破壊 → **1 failed**（family tie）

## 設計決定

1. **confirmed-zero 固定 = 撲滅同梱なし** — REQ-394 同型 precedent を踏襲。stale-comment は REQ-391〜394 撲滅済みの残骸であり、過去 iteration が修正済みの class。新規 site を意識的分類する gate（ALLOWED/ERADICATED ledger）だけが診断価値
2. **phrase は実測 roster から構築** — REQ-395 three-way guard drift 教訓の proactive 反映。ALLOWED 0 row / ERADICATED 0 row という phrase を hardcode せず、guard の自動計上から構築することで「spec 数値だけ書き換えても RED」「roster を 1 件変更しても spec 編集なしで RED」の双方向を構造的に防止
3. **stale-comment は REQ-397 と直交** — REQ-397 type-system bypass（`as any` / `: any`）とは検出対象が異なる（comment vs type system）。REQ-396 を独立 REQ 番号で切り出すことで reason 衛生（comment 系は 1 分類・type 系は 4 分類で異なる）を保つ
