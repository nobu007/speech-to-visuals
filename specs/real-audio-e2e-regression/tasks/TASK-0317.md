## 主要実装項目

### 1. §8.6 transcription 測定器セクション新設 🔵

**信頼性**: 🔵 *architecture.md「測定値の記録先」節・QUALITY_METRICS §8.5（D-3 前例・実在）より*

**実装ファイル**: `docs/architecture/QUALITY_METRICS.md`

§8.5「Diagram Type Detection Accuracy」と同型で §8.6 を新設:

- 測定コマンド 2 本（E2E: `npm run pipeline:test:audio`・file 単体: `npm run transcribe` 系ではなく `scripts/measure-transcription-accuracy.ts`）
- fail-loud 契約（placeholder run は測定ではない・corpus 空は exit 1）
- whisper binary / model の取得手順（`npx whisper-node download` 等・`STV_WHISPER_MODEL`）— repo に commit しない
- §3.1 記録の前提（corpus 整備 + 実測 run + artifact commit の同一 PR）

### 2. TC-407-02 guard（§3.1 未測定維持の強制）🔵

**信頼性**: 🔵 *TC-407-02 検証コマンド「corpus 空状態での §3.1 実測値記載を検出する guard」より*

**実装ファイル**: `tests/guards/` 配下（既存 guard suite の慣例に従う）🟡（guard の実装形状 — source-anchored `readFileSync` 検査か corpus 実体走査かの組合せは実装時に既存 guard 慣例へ合わせて確定）

- `public/audio/` を実走査し、audio file × 参照 pair が 0 件のとき: QUALITY_METRICS §3.1 Transcription Accuracy 行が「未測定」を含むことを検査
- corpus に実音声がある場合: §3.1 が実測値（WER / CER の数値 + artifact path）であることを要求（未測定のまま放置できない逆向きの ratchet）
- 常に実行可能な形にする（CI 上で whisper が無くてもこの guard 自体は green/red を判定できる — docs と corpus の静的検査）

### 3. §3.1 記載値 = artifact 一致 guard（設計決定 D5）🔵

**信頼性**: 🔵 *architecture.md 設計決定 D5・dataflow「データ整合性の保証」より*

- §3.1 に実測値が記載されている場合、`docs/architecture/measurements/transcription-e2e-v1.json` が存在し、記載の WER/CER・測定日が artifact の summary と一致することを検査
- artifact の数値だけ更新して §3.1 を更新しない逆方向の drift も検出（記載 ↔ artifact の双方向一致）

### 4. 実測 run と artifact（実行時手順 — maintainer/実行者の責務）🔵

**信頼性**: 🔵 *architecture.md「測定 artifact」節・D7 より*

- whisper binary + model を §8.6 手順で取得し、`npm run pipeline:test:audio -- --output docs/architecture/measurements/transcription-e2e-v1.json` で実測 run → artifact を commit → §3.1 を実測値で更新（en は WER・ja は CER を参照・Processing Speed は `transcriptionRtf` 実測値で `2.0x` を置換）を同一 PR で行う
- ja 実音声（TASK-0315 の maintainer 録音）が揃うまで en のみで実測可能なことを §8.6 に明記（ja は CER 主体・report は両 metric を持つ）
- **AI 実装 agent は binary/model 取得や録音を待たずに本 task の guard/docs を完了できる**（実測 run は手順の文書化と guard による出典強制で担保 — 実行は測定実行者）
