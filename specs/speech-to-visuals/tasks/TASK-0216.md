## タスク概要

`monitoring.ts` のエラーレスポンス処理で、`sendError()` 呼び出し後の `return` 忘れにより "Cannot set headers after they are sent" エラーが発生するリスクがある。また、主要な非同期ハンドラ（`getDashboardData` 等）にタイムアウト保護がなく、重い処理が応答をブロックする可能性がある。さらに、Zod validation errorで最初のissueのみを返しており、クライアントが全てのバリデーションエラーを一度に認識できない。

## 実装詳細

### 1. sendError()呼び出し後のreturn追加 🔵

**信頼性**: 🔵 *ソースコード監査より*

複数のルートハンドラで、`sendError()` を呼び出した後に `return` がないため、後続のコードが実行され、レスポンスヘッダーの重複送信エラー（"Cannot set headers after they are sent"）が発生する可能性がある。特に `catch` ブロック内の `sendError()` 呼び出し後に `return` を追加する。

**対象ファイル**: `src/api/routes/monitoring.ts` (行87-94周辺)

**実装内容**:
- 全ての `sendError()` 呼び出し後に `return` 文を追加
- `try/catch` ブロックの制御フローを見直し、エラー後に処理が継続しないことを保証
- 特に `GET /metrics`、`GET /cost`、`GET /trends` 等のハンドラを確認

### 2. 重い処理のAbortSignalタイムアウト追加 🟡

**信頼性**: 🟡 *タイムアウト値の適切な設定は実行時検証が必要*

`getDashboardData()` 等の重い処理にタイムアウト保護を追加する。長時間実行される処理がクライアントの接続タイムアウトを引き起こす前に、サーバー側でタイムアウトしてエラーレスポンスを返す。

**対象ファイル**: `src/api/routes/monitoring.ts`

**実装内容**:
- `Promise.race` パターンで処理とタイムアウトを競合させる
- タイムアウト時間は設定可能とし、デフォルト10秒
- タイムアウト時は503 Service Unavailable を返す
- AbortSignalで実際の処理もキャンセル（TASK-0213のパターンを適用）

### 3. Zod validation errorの全issues返却改善 🟡

**信頼性**: 🟡 *エラーレスポンス形式の変更はAPI利用者への影響あり*

`GET /trends` のZod validation（行116）で、最初のissueのメッセージのみを返している。全てのissuesを配列で返すよう改善し、クライアントが一度に全てのバリデーションエラーを認識できるようにする。

**対象ファイル**: `src/api/routes/monitoring.ts` (行116)

**実装内容**:
- `parsed.error.issues[0]?.message` から `parsed.error.issues` 全体に変更
- 各issueの `path`、`message`、`code` を含む構造化されたエラーレスポンスを生成
- レスポンス形式: `{ error: 'VALIDATION_ERROR', details: [{ path, message, code }, ...] }`
- 既存のクライアントは `details` がなくても `error` フィールドで判定可能（下位互換性維持）

## 注意事項

- `return` の追加は、Express.jsのミドルウェアチェーンにおける制御フローに影響を与えないよう注意すること

- AbortSignalのクリーンアップはTASK-0213と同じパターン（timer競合 + clearTimeout）を使用する
