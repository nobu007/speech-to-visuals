## 背景

Phase 181〜183（REQ-383〜385）が `src/quality/quality-monitor.ts` の Custom Instructions Compliance 系評価の捏造 leg を撲滅した際、**同一 file の performance 評価 2 leg** に同型 sibling が残存していた（**missed-sibling-site class** — 本 repo の CORE recurring bug class）。Phase 172（REQ-369〜371）の canonical estimator 委譲は SimplePipeline / GeminiAnalyzer が対象で、本 file は未処理:

| site | 旧実装 | 実欠陥 |
|---|---|---|
| `assessProcessingSpeed(processingTime)` | `const assumedAudioDuration = 60000`（`// Assume 60s audio`）を分子に speed ratio 計算 | **required top-level `PipelineResult.duration`（ms）が存在するのに捏造定数を使用**（REQ-383 の processingTime leg と同型の required-field-over-fabrication）。12s content を 10s で処理した run（実 ratio 1.2 → score 0.6）を 6x-realtime（score 1.0）と過大評価し、逆に 300s content の高速処理を過小評価 |
| `assessMemoryUsage()` | `const currentMemoryMB = 128`（`// Current observed peak`）→ 常に `1.0` | **根拠ゼロの定数 always-pass**。performanceScore の 30% 重みを毎 run 無条件で満点供給し、overallScore に +0.09 — 実質 0.61 の run を `checkDeploymentReadiness` の 0.7 gate に押し上げ得る masking。REQ-383 が sibling leg（evaluateIterationQuality）で確立した実測 signal `metrics.memoryUsage`（bytes）を読まない |

## 修正

1. **`assessProcessingSpeed(contentDurationMs, processingTime): number | null`** — 分子を required `result.duration` に読み替え。duration が非正・非有限（hard-error path の `duration: 0` 等）は vs-realtime 比が**未計測** → `null` 返し
2. **`assessMemoryUsage(result): number | null`** — optional `result.metrics?.memoryUsage`（bytes）を実測値として読み、既存 256MB target rubric（≤128MB → 1.0・≤256MB 線形・超過 → 0.0）で評価。未計測（field なし / 非有限）は `null` 返し
3. **`assessPerformance` の weighted-sum から null leg を除外** — `score` と `maxScore`（分母）の両方に加算しない（REQ-383 の keyset-derived denominator と同型の measured-only 除外）
