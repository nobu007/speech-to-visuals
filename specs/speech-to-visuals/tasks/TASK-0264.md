## 背景

同名 2 monitor が意図的に別 scale を保持している:

| monitor | score | scale | gate |
|---|---|---|---|
| `src/quality/quality-monitor.ts` | `QualityAssessment.overallScore` ほか 4 score | **0-1**（0-1 assessor の加重和） | deployment gate 0.7 / 0.9 |
| `src/pipeline/quality-monitor.ts` | `QualityReport.overallScore` | **0-100**（base 100・違反減点・bonus +5） | status tier 90/75/60/40 |

2026-08-22 時点で両方を同時 import する production consumer はゼロ（0-1 側は main-pipeline が barrel `@/quality` 経由、0-100 側は orchestrator / simple-pipeline / gemini-analyzer / regression-detector / improvement-detector が直接 import）— つまり risk は **latent**。だが 0-1 側 interface に scale doc が一切なく、未来の cross-wired import は silent 100x error（0-1 の 0.85 が `>= 70` gate で fail・0-100 の 85 が `>= 0.7` gate を pass）になる。SceneGraph ms/s ×1000 と同型の「無文書単位」class が score 軸に存在した。

## 修正

### `src/quality/quality-monitor.ts` — scale doc comment 付与

`QualityAssessment` の 4 score（overall/performance/accuracy/reliability）宣言に `// 0-1` + sibling 0-100 monitor との cross-read 禁止を明記した doc comment block を追加（0-100 側は既存の `// 0-100` doc あり）。

### 新設 `tests/guards/quality-monitor-dual-scale.test.ts`（7 tests・4 legs）

1. **leg 1 behavioral（0-1 側）**: rich success fixture（分離 2 node layout + summary/keyphrases + success PipelineResult）で `assessPipelineQuality` の 4 score すべて ∈ [0,1]・> 0（anti-vacuity）。×100 rescale は即 RED
2. **leg 2 behavioral（0-100 側）**: singleton の fresh module registry を利用し宣言順で (i) no-history → 0 / 'critical' fail-closed (ii) measured-good metrics → **overallScore > 1**（scale 弁別子）かつ ≤100 / 'excellent'
3. **leg 3 source-anchor**: 両 overallScore 宣言の scale doc（`// 0-1` / `// 0-100`）を正規表現で検証。`// 0-1` は `(?!\d)` lookahead で `// 0-100` 誤一致を排除
4. **leg 4 cross-wiring invariant**: 非 test src 全ファイル（`__tests__`/`__mocks__`/`*.test.*` 除外・anti-vacuity で files > 100・fractional ≥1・percent ≥3）が両 monitorを同時 import していないこと。barrel import（`@/quality` が fractional monitor を re-export）も 1-hop で解決して分類

### 台帳 dogfood: MW-046 entry + appendix row

- MW-046 entry + appendix row 同梱・`tests/guards/mutation-witness-ledger.test.ts` 監査 pin **≥45 → ≥46**

**設計決定**: scale 統合（0-100 側を 0-1 へ変換）は行わない — 0-100 側は status tier と base-100 deduction 計算に深く結合し、統合は全 5 consumer の閉じ直しを要求する design-heavy 変更。契約文書化 + cross-wiring 検出で latent 期間の安全性を担保する方針（requirements.md REQ-382 scope 決定に同一文言）。
