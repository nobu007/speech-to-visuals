## 背景

Phase 181〜184（REQ-383〜386）が `src/quality/quality-monitor.ts` の未計測 leg を measured-only 化した結果、`evaluateIterationQuality` の memoryUsage leg と `assessPerformance` の memory leg は**実測 `result.metrics?.memoryUsage`（bytes）が存在しない run から除外**されるようになった。しかし **MainPipeline は同 field を一切生産していなかった**（`createSuccessResult` の metrics は `totalRetryAttempts` のみ）ため:

- 両 leg は本番 runtime（Node — 常に正の heap を報告）でも**恒久的に除外**され続け、契約は dead contract 化
- measured-only 化の実効（実測 512MB run の減点・💾 recommendation 発火）は test fixture でしか観測不能

TASK-0268 の設計決定「memoryUsage producer 計装は作成しない（fail-closed が計装を促す）」を、make-run steering の直接指定（計測の生産を実装して leg を live 化）により解除・履行する。

## 実装

1. **`src/pipeline/memory-usage-metrics.ts`（新規 pure helper）** — `peakHeapUsedBytes(samples: Iterable<number>, liveReading: number | null): number | null`
   - 正の有限値のみを測定とみなし、その max（peak）を bytes そのまで返す
   - **0 は未計測**: stv-core `getMemoryUsage()` は memory API のない runtime で `{heapUsed: 0}` を返す。0 を publish すれば REQ-386 rubric は「0 bytes = excellent」の always-pass を得る（hardcoded 128MB 撲滅と同型の masking が unit 経由で再開）。`initializePerformanceMonitoring` の `heapUsed > 0` discipline と同一
   - NaN / ±Infinity / 負は skip（実測値を poison しない）
   - pure 抽出の理由: no-API branch は実 Node backend 対しては再現不能 — module mock なしに契約を全分岐で検証可能にする
2. **`src/pipeline/main-pipeline.ts`** — `measuredPeakHeapUsedBytes()`（`memorySnapshots.values()` + `readMemoryBackend().heapUsed` — REQ-358 finite-or-null boundary）を `createSuccessResult` から呼び、**conditional spread** で `metrics.memoryUsage` を populate（null は field omit）。`createSuccessResult` は全 3 成功経路（framework-integrated / parallel / sequential）が通り、両 `assessPipelineQuality` call site（L520/L875 相当）が結果構築後に読む単一 chokepoint
3. **`src/pipeline/types.ts`** — `ExtendedPipelineMetrics.memoryUsage` doc に producer と measured-only omit 契約を明記
