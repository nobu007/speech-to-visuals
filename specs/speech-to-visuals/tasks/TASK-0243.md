## 終了条件到達の判定 wiring（spec → guard 連動）

`tests/guards/non-null-assertion-census.test.ts` に以下の acceptance test を追加し、終了条件そのものを機械判定する（任意の **新しい** ラウンド提案は、その前段で `npx jest tests/guards/non-null-assertion-census.test.ts` を通過すること）:

```ts
describe('ratchet exit condition (TASK-0243 / REQ-346)', () => {
  it('tests total pin has not regressed past the gate (≤ 100)', () => {
    expect(PINNED['tests (excl. __mocks__)']).toBeLessThanOrEqual(100);
  });
  it('tests/unit directory pin has hit exact-0', () => {
    expect(TESTS_DIR_PINS['unit']).toBe(0);
  });
  it('once both gates hold, the next round must NOT decrement a tests pin (caller-side rejection)', () => {
    // guard: if we reach here, the ratchet mechanism is exhausted;
    // subsequent rounds that propose ANOTHER round of test `!` rewrite
    // for non-real-path reasons should be flagged.
    const stillRoom = PINNED['tests (excl. __mocks__)'] > 100 || TESTS_DIR_PINS['unit'] > 0;
    expect(stillRoom).toBe(false); // both gates must hold for this assertion to be meaningful
  });
});
```

この 3 ケースが GREEN になった以降、TASK-0244 以降のラウンド提案では `tests/unit exact-0` または `tests total pin ≤ 100` のどちらかを **引き下げてはならない**（monotonic decrease を打ち切り、上限緩和による growing-back を構造的に防ぐ）。

## 終了条件到達後の obligation（次サイクル義務）

TASK-0242 までの pure-ratchet で残った `!` の **すべて** は「既に正しく動作している helper の throw 確認」であり、AI_HUB_MAKE_RUN_FEEDBACK が指摘するとおり新しい危険を露出しない。終了後の cycle は **必ず** 以下のいずれかを 1 件以上含むこと（最低単位の AC）:

### 義務 A: 実 production null 経路の修正（mutant 実測可能なもの）

`tests/guards/non-null-assertion-census.test.ts`（PINNED commentary + TESTS_DIR_PINS）と `mutation-witness-ledger.test.ts` を逆引きし、tests 側で throw helper に置換された各 pattern について **src/ 側の API 契約**（`T | null` / `T | undefined` 戻り）と **呼び出し側**を 1 件以上 harden する。harden の形:

- `T | null` を返す function の caller で `if (result === null) throw` 化（result-only falsy 問題の解消）
- optional chaining 化（`a?.b?.c` → 中間で落ちない導線）
- `?? NaN` / `?? 0` の正規化閾値を `?? GATE-FAIL` に揃える（同 ledger の record-vs-gate divergence 分類）

最低 1 件は MW-022 として mutation-witness-ledger.md に追記すること（MW-014〜021 のフォーマット準拠）。RED → fix → GREEN の 3 ステップ実測と、救済 revert の余裕を残さない fail-loud な wiring を含むこと。

### 義務 B: architecture.md mirror 同期の spine hook 化

requirements.md（正本）と architecture.md（mirror）の二重管理は AC mirror 同期を「人間の手作業」経由で spine DONE 判定から切り離せない原因になっている。spine が mirror 同期を **PR / precommit ではなく spine:children:begin 直前の build hook / Makefile target** で再生成する場合のみ DONE とみなす。`make` target `make sync:mirror-from-requirements` を追加し、`specs/_doc_spine.yml` の post-step として配線する。
