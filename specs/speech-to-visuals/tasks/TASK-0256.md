## 背景

steering feedback（Phase 169 後）は「ratchet 系自己言及的 churn を生成せず次の義務へ移行」を指示（具体的な T0244/freeze-guard/RATCHET_CEILING は cross-repo contamination — `specs/task-0244-test-inventory-ratchet/` は trans_parency_os_private に存在）。本 repo の次の義務は TASK-0255 §残存 obligation と memory L3 台帳 hunt-order #1 の **「0.85 metric-DEFAULT coupled-to-GATE-threshold（11+ sites）— default flip = gate flip」**。

hunt の結果、live instance を特定: `src/monitoring/real-time-performance-monitor.ts` の `getSnapshot()` は

```ts
quality: {
  transcriptionAccuracy: 0.90, // Populated externally
  layoutOverlapRate: 0,         // Populated externally
  avgSceneQuality: 0.85         // Populated externally
}
```

および `llm.avgFlashResponseTime/avgProResponseTime: 0`（同コメント）を返すが、**外部から populate する producer は repo 内に一切存在しない**（`updateQuality`/`setQuality` 系 setter なし・消費側 grep で確認）。これらの捏造定数が `src/quality/adaptive-quality-gates.ts` の DEFAULT gate と正確に結合していた:

| DEFAULT gate | 比較 | 捏造値 | 常時結果 |
|---|---|---|---|
| Transcription Accuracy（**blocker**・adaptable） | `gte` DEFAULT_TRANSCRIPTION_ACCURACY_THRESHOLD (**0.85**) | 0.90 | 恒久 PASS |
| Layout Overlap Rate（**blocker**） | `eq` 0 | 0 | 恒久 PASS |
| LLM Response Time（major・adaptable） | `lt` 15000 | 0 | 恒久 PASS（"瞬時に応答"） |

さらに `adaptable: true` の Transcription Accuracy gate は `updateAdaptiveThresholds` が捏造 0.90 を baselineValue/historicalValues に投入し**閾値適応を汚染**（REQ-360 が null について閉じた poisoning 経路の fabrication 版 — 捏造値に向かって閾値が適応する）。「default flip = gate flip」: 定数 0.90 を 0.8 に変えただけで blocker gate が無実の critical FAIL になる。

## 修正

REQ-358〜360（Phase 166）が `system` memory 4 field に確立した **finite-or-null 契約を拡張**:

1. `PerformanceSnapshot` 型: `quality` 3 field と `llm.avgFlashResponseTime`/`avgProResponseTime` を `number | null` に（null = no reading）。doc comment に「never fabricated constants: 旧 0.90/0/0.85 は blocker gate 閾値と正確に結合し恒久 green だった」旨を記録
2. producer: 5 field とも `null` を返す
3. **契約境界は変えない**: gate の無い display-only accumulator（`flashUsagePercent`/`proUsagePercent`/`estimatedCostSavings`・`cpuUsagePercent`）は有限 0 のまま（「nothing recorded yet」は 0 が正直）
4. 消費側は既存機械に乗るのみ: `evaluateGate` は null を **METRIC UNAVAILABLE fail-loud**（REQ-360 で実装済み）・`updateAdaptiveThresholds` は null round を skip（同）・METRIC_EXTRACTORS の doc comment を拡張

消費側影響は事前に全数列挘して狭いことを確認: AdminAnalyticsDashboard は `pipeline.p95ProcessingTime` のみ読む・`generateRecommendations` は `system.memoryUsagePercent` のみ読む・health-check fallback の 0 は `number | null` に assign 可能・adaptive-quality-gates 自体に production wiring は無し（テストと将来 wiring の誠実性を保証）。
