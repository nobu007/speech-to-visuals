## 設計決定

1. **phrase は pin 値の二重管理をしない** — THREE_WAY row に期待数を hardcode せず guard 実測から phrase を構築する。roster が変われば phrase が自動的に新数値を要求し、spec と guard のどちらか一方だけの編集では必ず RED（期待値の第三の管理場所が drift する課題を構造的に排除）
2. **解体 ≠ 削除** — end state の ratchet file は恒久 no-regression guard として存続するのが正しい解体。保護の削除には「厳格に強い代替機構」（ESLint rule 等）を同じ変更で示す専用 REQ を要求する。fold-census も anti-re-inline 保護（delegation target 存在 pin）は count ratchet より長寿命と明記
3. **drift の訂正は silent に行わない** — REQ-392 の数値訂正には「当初 32/27 と宣言・実 34/29 で ship・REQ-395 three-way guard が発見」という経緯を本文に残し、REQ-395 も drift 実例として引用（数値だけ直して経緯を消すと、昇格の動機となった実例が失われる）
