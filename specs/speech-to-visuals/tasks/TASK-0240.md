## 実施内容（2026-08-20 完了）

### 1. analysis/llm-cache-debounce.test.ts 20 node → 0（fail-loud `requireDisk()`）

`readCacheFile()`（`{ entries: … } | null` を返す fs 読み取り helper）の `disk!.entries` / `readCacheFile()!.entries` / `updated!.entries` の 3 形態を `requireDisk()` に集約:

```ts
function requireDisk(): { entries: Array<{ key: string; data: string }> } {
  const disk = readCacheFile();
  if (disk === null) {
    throw new Error(`expected persisted cache file at ${cachePath}`);
  }
  return disk;
}
```

**null-guard 根拠**: `readCacheFile()` は不在時に `null` を返すため undefined でなく **null** を guard（Phase 151 と同一）。throw メッセージに `cachePath` を含め欠落時にどのパスが空か診断可能。直前の `const disk = readCacheFile(); expect(disk).not.toBeNull();` 対は helper の throw が同保証を担うため折りたたみ。

### 2. analysis/budget-alert-boundary.test.ts 11 node → 0（fail-loud `requireAlert(alerts, type)`）

`alerts.find(a => a.type === 'session')` 等の `sessionAlert!` / `dailyAlert!` を型付き lookup helper に:

```ts
function requireAlert(alerts: BudgetAlert[], type: BudgetAlert['type']): BudgetAlert {
  const found = alerts.find((a) => a.type === type);
  if (found === undefined) {
    throw new Error(`${type} alert not fired`);
  }
  return found;
}
```

`BudgetAlert` と `BudgetAlert['type']` を src の export から import し throw メッセージが「どの種類の alert が発火しなかったか」を表明。`not.toBeNull()` / `toBeDefined()` 対は折りたたみ（宣言が不要になった site は宣言ごと削除）。

### 5. visualization/cycle-strategy.test.ts 16 node → 0（構造型 `centerXOf`/`centerYOf` + inline NaN 保存境界）

root 側（`@stv/core` 型を直接 import しないテスト）は**構造型**で十分:

```ts
function centerXOf(node: { x: number; width?: number }): number {
  return node.x + (node.width ?? Number.NaN) / 2;
}
```

重なり判定境界 `n0.x < n1.x + n1.width! && n0.x + n0.width! > n1.x` は helper 化せず inline `(n1.width ?? Number.NaN)` 置換（比較式の構造がヘルパ引数に合わないため）。**`?? Number.NaN` の根拠は Phase 152 と同一**: 旧 `width!` は checker 抑制のみで `width === undefined` なら旧コードは `NaN` を算出（比較 fail = RED）→ 同一の undefined→NaN 伝播を明示保存し matcher の `number | undefined` 型エラーも解消。

### 6. visualization/strategies/cycle-strategy.test.ts 13 node → 0（型付き `findNode`/`findEdge`/`centerXOf`/`centerYOf`）

strategies 側は `PositionedNode`/`LayoutEdge` を `@stv/core/types/diagram` から import し**型付き helper** とした:

```ts
function findNode(result: { nodes: PositionedNode[] }, id: string): PositionedNode
function findEdge(result: { edges: LayoutEdge[] }, from: string, to: string): LayoutEdge
function centerXOf(node: PositionedNode): number
```

**型付きが必須の根拠**: `LayoutEdge.from` は `string | undefined` 型のため、構造型 `{ from: string }` では `LayoutEdge[]` を引数に取れず tsc error（初回 `findEdge(result: { edges: Array<{ from: string; to: string }> })` で 7 件の新規 tsc error を出し修正）。戻り `LayoutEdge` が `.points` 等の下游 field 読みを型安全にする。

### 7. integration/pipeline-orchestrator-recovery.test.ts 13 node → 0（`requireMetrics` + `requireRecoveryReport` + `requireDefined`・cast 除去）
