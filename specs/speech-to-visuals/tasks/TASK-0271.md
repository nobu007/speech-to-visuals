## 背景

`src/quality/quality-monitor.ts` `assessLLMExtractionQuality` は (a) `metrics.entityExtractionF1Score` / `relationAccuracy`（ExtendedPipelineMetrics・"if ground truth is available"）があればそれを平均する measured branch と (b) なければ scene 構造から proxy を作る heuristic fallback の 2 branch を持つ。本 pipeline に ground truth は存在せず、同 field に書き込む producer はゼロ（grep 全 src で読み手 1 件・書き手 0 件）のため、**全実 run** が fallback を通る。その fallback が canonical single-source module `quality-estimators` と**異なる第三の scale**を再凍結していた:

| signal | canonical（quality-estimators） | 旧 fallback（quality-monitor） |
|---|---|---|
| entity 抽出品質 | `scoreNodeDensity`: 2-10 node/scene → **0.90** / 1 → **0.70** / else **0.50**・平均は **scenes-with-nodes** ベース | `avgNodes≥2→0.8 / ≥1→0.6 / else 0.3`・平均は**全 scene** ベース |
| relation 抽出品質 | avg edge density ≥1 → **0.85** / else **0.60** | `some(edges>0)→0.8 / else 0.5` |
| 失敗 run | `!success → 0`（正直） | **success 未参照**・構造があれば 0.8 を主張 |

影響: LLM 抽出 leg は accuracyScore の 20%（= overallScore の 8%）。healthy run で 0.875 が 0.8 に（false-penalty — REQ-386 の捏造 always-pass と逆方向だが機構は同一の duplicate-formula class）、**FAILED run で構造から 0.8 を捏造**し accuracyScore 0.93（readiness bar 0.8 超）を主張。quality-estimators の header 契約「pipelines と Phase 27 QualityMonitor が honest, identical quality signals を見る」に違反し、framework（`FrameworkQualityMetrics.entityExtractionF1` は canonical 値）と monitor の同 run 観測が恒久的に不一致。

## 実装

1. **pin 追加（fix 前 RED 4 実測）** — `src/quality/__tests__/quality-monitor.test.ts` describe `LLM extraction quality` 配下に `REQ-389: fallback delegates to the canonical estimator scale` を新設。全 assessor が deterministic な fixture で `accuracyScore` を exact pin: (a) healthy run 0.945（leg 0.875・旧 scale は 0.935）(b) singleton/no-edge 0.80（leg 0.65 = (0.70+0.60)/2・旧は 0.55 相当）(c) FAILED run 構造付き 0.77（leg 0・旧は 0.93）(d) canonical 推定値を metrics に与えた run と metrics なし run の accuracyScore 完全一致（measured branch と fallback の不一致不可能を 実行可能に証明）
2. **委譲 fix** — fallback 本体を `estimateEntityExtractionQuality(result) + estimateRelationAccuracy(result)) / 2` に置換（measured branch の `parts 平均` と同形）。旧の凍結定数・全 scene 平均・`some(edges)`・success 未参照を削除
3. **設計決定: ground-truth field への推定値 publish はしない** — REQ-387（memoryUsage producer）と違い `entityExtractionF1Score` は型 doc が "if ground truth is available" と宣言する ground-truth 専用 slot。proxy を F1 名の field に書き込むと捏造 class の再導入になるため、producer は作成せず measured branch は実 ground truth が来るまで dormant（test のみが明示的に与える現状を維持）。REQ-386 系との差分はこの設計判断の根拠
4. **MW-053 mutation 検証（3 独立 RED 実測）** — (a) 旧凍結 scale 再注入 → **4 failed / 46 passed**（healthy 0.945→`Received: 0.935`・singleton→0.79・FAILED run→`Received: 0.93`・branch 等価 の 4 site）(b) relation leg 欠落（entity のみ返す）→ **3 failed / 47 passed**（0.945→0.95・0.80→0.81・branch 等価）(c) estimator 呼び出しの success gate 解除（`{ ...result, success: true }`）→ **1 failed / 49 passed**（FAILED run pin のみ `Received: 0.945`）。各 revert（Edit 逆適用・`git checkout --` 不使用）で 50/50 GREEN 復元
