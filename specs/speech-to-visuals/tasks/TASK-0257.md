## 背景

Phase 170（REQ-364）は producer-less 5 field を finite-or-null 化し blocker gate の恒久 green を撲滅したが、make-run feedback は 2 点を指摘:

1. **fail-loud の行き先**: null のままでは monitor 起動後 1 リクエスト目まで LLM Response Time gate が METRIC UNAVAILABLE・`deploymentReady=false` が常態化する。monitor は既に LLM request を count している（`recordLLMRequest(model, responseTime, fromCache)` が Phase 154 から存在）ので **request start/end timing の producer が自然な次 TASK**。producer を作らない場合は「producer 不在 gate は fail-closed のまま計装を促す」設計決定を specs に記録すること。
2. **静的 guard**: `METRIC_EXTRACTORS` の `?? 定数` silent-pass 再注入は現在 MW-038 の runtime test でのみ検出される。静的 guard を追加しない限り次の再注入は review を素通りする。

## 修正

### REQ-365: monitor 側 per-model 累積 producer

`real-time-performance-monitor.ts`:

- counters に `{flash,pro}ResponseTime{TotalMs,Count}` 追加（`reset()` で消去）
- `recordLLMRequest` は先頭で `sanitizeFinite(responseTime)`（NaN/Infinity 除外）し、non-cached 完了のみ bucket に累積
- helper `classifyModelBucket(model)`: `flash`/`pro` substring 相互排他 — どちらも無い・両方含む（複合 `'pro+flash'`・`'cache'`）は `null` = per-model attribution なし
- `getSnapshot()`: `avgModelResponseTimeMs(totalMs, count)` = `count > 0 ? Math.round(totalMs / count) : null`

**設計決定（REQ-365）**: cache hit は per-model 平均から除外 — cache lookup は model を起動せず、~0ms を混ぜると lower-is-better gate を不当に GREEN 側へ傾ける微型捏造。

### REQ-366: llm-service wiring（報告点 5）

`src/analysis/llm-service.ts` の `execute()` が `realTimeMonitor.recordLLMRequest` に報告:

| 経路 | 報告 |
|---|---|
| cache hit | `('cache', elapsed, true)` |
| primary 成功 | `(primaryModel, responseTime, false)` |
| primary 即時失敗 | `(primaryModel, elapsed, false)` — 実消費 latency は実測 |
| fallback 成功 | `(fallbackModel, responseTime, false)` のみ — **中間 primary 失敗は報告しない** |
| 全滅 | `` (`${primary}+${fallback}`, elapsed, false) `` — 複合ラベル → attribution なし |

**設計決定（REQ-366）**: LLM not-enabled 経路は報告しない（LLM interaction が存在しない）。依存方向 analysis→monitoring（monitoring は analysis を import しない・循環なし）。

### REQ-367: 静的 guard

`tests/guards/adaptive-gates-extractor-no-literal-fallback.test.ts`（新規・source-anchored `readSource`）: METRIC_EXTRACTORS block 内の `\?\?\s*<数字>` / `\|\|\s*<数字>` を禁止。anti-vacuity: block 検出・長さ>500・`: s =>` arrow 数 = 18（field 型 annotation の `=>` を除外するため `: s =>` で計数）・全 18 key 存在 pin — block が空に縮むと guard が恒真化するのを防ぐ。

### REQ-368: MISSED-SIBLING-SITE

`health-check-service.ts` の catch-fallback minimal metrics（`getSnapshot()` throw 時）が契約 9 field に捏造 0 を再注入していた（REQ-359/364 の sibling）→ system memory 4・per-model LLM 2・quality trio 3 を明示 `null`、display accumulator（`flashUsagePercent`/`cpuUsagePercent`）のみ有限 0。

### 設計決定: producer-less gate は fail-closed のまま

quality trio（`transcriptionAccuracy`/`layoutOverlapRate`/`avgSceneQuality`）は本 TASK でも producer を作らない。正解ラベル/実測 overlap は別 subsystem 由来で最小 verifiable 範囲を超え、REQ-364 の意図（METRIC UNAVAILABLE fail-closed が計装を促す）は producer が無い限り有効。当該 3 gate は計装 TASK まで「計測なし = RED」表示を維持する（要件文に明記）。
