## 実装詳細

### 1. 統一エラーハンドラー (src/api/middleware/error-handler.ts) 🔵

**信頼性**: 🔵 *api-endpoints.md エラーレスポンス共通フォーマット・PIPELINE_FLOW.md §7.2より*

Express エラーハンドリングミドルウェアの実装。

エラーレスポンス形式:
```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "エラーメッセージ",
    "details": {}
  }
}
```

カスタムエラークラス:
- `AppError`: 基本アプリケーションエラー（statusCode, code, message, details）
- `ValidationError`: 400 バリデーションエラー
- `AuthenticationError`: 401 認証エラー
- `AuthorizationError`: 403 認可エラー
- `NotFoundError`: 404 リソース未検出エラー
- `RateLimitError`: 429 レート制限エラー
- `ExternalServiceError`: 502 外部サービスエラー

機能:
- エラーのログ出力（構造化ログ）
- 本番環境ではスタックトレースを隠蔽
- 開発環境ではスタックトレースを含める
- 不明なエラーは500として処理

**実装ファイル**: `src/api/middleware/error-handler.ts`

### 2. レート制限ミドルウェア (src/api/middleware/rate-limit.ts) 🔵

**信頼性**: 🔵 *NFR-103・api-endpoints.md セキュリティ・package.json 依存関係より*

express-rate-limit を使用したレート制限の実装。

設定:
- グローバル制限: 100リクエスト/15分
- API 制限: 30リクエスト/1分
- バッチエンドポイント: 5リクエスト/1分
- 信頼済みプロキシの設定
- 制限超過時のレスポンス: 429 Too Many Requests
- カスタムヘッダー: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`

**実装ファイル**: `src/api/middleware/rate-limit.ts`

### 3. Helmet セキュリティヘッダー (src/api/middleware/security.ts) 🔵

**信頼性**: 🔵 *NFR-103・api-endpoints.md セキュリティ・architecture.md ミドルウェアより*

Helmet を使用したセキュリティヘッダーの設定。

設定:
- `contentSecurityPolicy`: 適切なCSPディレクティブ
- `hsts`: Strict-Transport-Security（本番環境のみ）
- `xFrameOptions`: DENY
- `xContentTypeOptions`: nosniff
- `referrerPolicy`: strict-origin-when-cross-origin
- 開発環境では CSP を緩和（インラインスクリプト許可）

**実装ファイル**: `src/api/middleware/security.ts`

### 4. JWT 認証ミドルウェア (src/api/middleware/auth.ts) 🔵

**信頼性**: 🔵 *api-endpoints.md 認証・NFR-101・architecture.md 認証方式より*

JWT 認証ミドルウェアの実装。

機能:
- `Authorization: Bearer {token}` ヘッダーからトークンを抽出
- Supabase JWT の検証
- ペイロードからのユーザー情報（sub, email）を `req.user` に設定
- 認証失敗時: 401 Unauthorized
- オプショナル認証: トークンがあれば検証、なければ `req.user = null`
- `requireAuth()`: 認証必須ミドルウェア
- `optionalAuth()`: 認証任意ミドルウェア

**実装ファイル**: `src/api/middleware/auth.ts`

### 5. リクエストバリデーションミドルウェア (src/api/middleware/validate.ts) 🔵

**信頼性**: 🔵 *api-endpoints.md リクエスト形式・PIPELINE_FLOW.md §7.2より*

リクエストボディ・パラメータのバリデーションミドルウェア。

機能:
- `validateBody(schema)`: リクエストボディのバリデーション
- バリデーションエラーの統一フォーマット化
- エラーレスポンス例:
  ```json
  {
    "success": false,
    "error": {
      "code": "VALIDATION_ERROR",
      "message": "Invalid request body",
      "details": {
        "files": ["files is required"],
        "concurrency": ["concurrency must be between 1 and 10"]
      }
    }
  }
  ```

**実装ファイル**: `src/api/middleware/validate.ts`

## 単体テスト要件

**Then**: ステータス400でバリデーションエラーレスポンスが返る

**テストファイル**: `src/api/middleware/__tests__/error-handler.test.ts`

### テストケース3: レート制限テスト 🔵

**Given**: レート制限が30リクエスト/1分に設定されている
**When**: 短時間に31回リクエストを送る
**Then**: 31回目がステータス429で拒否される

**テストファイル**: `src/api/middleware/__tests__/rate-limit.test.ts`

### テストケース4: JWT 認証成功テスト 🔵

**Given**: 有効な JWT トークンが Authorization ヘッダーに含まれる
**When**: `requireAuth()` ミドルウェアを通過する
**Then**: `req.user` にユーザー情報が設定され、次のハンドラーが呼ばれる

**テストファイル**: `src/api/middleware/__tests__/auth.test.ts`

### テストケース5: JWT 認証失敗テスト 🔵

**Given**: Authorization ヘッダーがない、または無効なトークン
**When**: `requireAuth()` ミドルウェアを通過する
**Then**: ステータス401で `AuthenticationError` が返る

**テストファイル**: `src/api/middleware/__tests__/auth.test.ts`

### テストケース6: オプショナル認証テスト 🔵

**Given**: Authorization ヘッダーがない
**When**: `optionalAuth()` ミドルウェアを通過する
**Then**: `req.user` が `null` に設定され、次のハンドラーが呼ばれる

**テストファイル**: `src/api/middleware/__tests__/auth.test.ts`

### テストケース7: リクエストバリデーションテスト 🔵

**Given**: バリデーションスキーマが `files` を必須としている
**When**: `files` プロパティのないリクエストボディで `validateBody()` を通過する
**Then**: ステータス400でバリデーションエラーが返る

**テストファイル**: `src/api/middleware/__tests__/validate.test.ts`

### テストケース8: Helmet ヘッダー確認テスト 🔵

**Given**: Helmet セキュリティミドルウェアが適用されている
**When**: 任意のエンドポイントにリクエストを送る
**Then**: レスポンスヘッダーに `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` が含まれる

**テストファイル**: `src/api/middleware/__tests__/security.test.ts`

## 注意事項

- エラーメッセージには機密情報（API キー、トークン、スタックトレース）を含めないこと（NFR-101）
- レート制限の設定値は環境変数で調整可能にすること
- Helmet の CSP 設定は開発環境と本番環境で切り替えること
- JWT 検証で使用するシークレットはサーバー側の環境変数のみから取得すること
- バリデーションスキーマは各エンドポイントのテストで再利用可能にすること
